1. Start making sound

  1. Load the complete sonic_pi_vst3.vst3 folder as an instrument in your host.
  2. Activate the host’s audio engine and connect the instrument’s stereo output to the host output.
  3. Wait for the Sonic Pi ready message, choose Code, and enter a program.
  4. Choose Run. Choose Stop to stop its jobs.
use_bpm 110

live_loop :pulse do
  play 60, amp: 0.5
  sleep 1
end

The instrument uses its own Sonic Pi clock. It does not synchronize to the DAW tempo or transport, and these editor features do not add MIDI routing.

Opening a saved DAW project restores source text, not playback. Press Run when you are ready.

2. Reuse snippets without losing code

The Snippets button opens the portable Snips tool. Every time you open its menu, it reads the Snips folder again. Add or edit a UTF-8 .rb or .txt file there, then reopen the menu. No restart is needed.

  1. Choose Code.
  2. Open Snippets, then select Append: filename.
  3. The file is appended at the end, separated by a blank line. Existing source is kept even if you had selected all the text.
  4. Review the combined program, rename any duplicate live loops, then choose Run separately.

Undo last snip append restores the source from before the latest append. It refuses to discard manual changes made afterwards. The folder menu also opens the Snips directory and the bundled check report.

The six supplied files cover a live loop, a synth/note, reverb, a drum sample, a timed note pattern and a thread. The Windows packaging check executes every snippet in the shipped Snips folder against that package’s Sonic Pi runtime, checks for runtime errors and verifies non-silent audio. Its results and exact tested source are written to Help/snippet-checks.html.

The report applies to the source that was tested at build time. Files you add or edit later are not automatically run or certified. Snippets are Ruby/Sonic Pi code and can access files or perform other actions. Review unfamiliar snippets before running them.

The menu supports up to 128 top-level files. Subfolders and symbolic links are not loaded. Empty snippets and additions that exceed the 32,000-byte Run limit are rejected without changing your source. Snips append only in Code view, never into a generator or preview.

3. Files and portable folders

sonic_pi_vst3.vst3/
├── Contents/             Plug-in binary and bundled runtime
├── Snips/                Reusable Sonic Pi .rb / .txt snippets
├── Files/
│   ├── Code/             Your Sonic Pi source files
│   └── Generators/       Your trusted Ruby generator scripts
├── Help/
│   ├── editor.html       This offline guide
│   └── snippet-checks.html
└── RuntimeData/          Runtime logs and Sonic Pi user configuration

Open and Save use Files/Code in Code view and Files/Generators in Script view. Subdirectories are supported. To import an existing file, copy it into the appropriate portable directory first. Choosing a path outside that directory is rejected instead of silently creating a dependency elsewhere.

Save writes to a temporary file in the destination directory and replaces the original only after the write succeeds. The title shows an asterisk when the active buffer differs from its last external-file save. Open warns before replacing unsaved source.

Moving or upgrading

  • Put the whole .vst3 folder in a location your user account can write to, such as a portable plug-in directory. A protected system folder can prevent saves or runtime startup.
  • Close the host, then copy the whole folder to the new machine or drive. Do not copy just the binary under Contents.
  • Back up Files and Snips before replacing or upgrading the plug-in bundle. Your DAW project and portable folder are separate backups.
  • The editor resolves these folders from the plug-in’s current location. It does not save an installation drive letter or use AppData for its runtime home.
  • Absolute paths or external samples you write into your own Ruby code are your responsibility. Copy that data and update those paths when moving.

DAW state versus external files

Saving the DAW project embeds both the Code and Script buffers. Restoring it does not run code, restore active jobs, keep previews, or restore trust approval. External Save destinations are cleared after project restore: choose a destination again. Older code-only states load with the starter generator. Preview cannot be opened over or saved directly; apply its output to Code first.

Older versions used an AppData/home runtime folder. Existing external files are not deleted or migrated automatically. Copy the source or configuration you want into this portable setup yourself.

4. Ruby code generators

Script is a separate Ruby buffer. The script’s final expression must return a String containing Sonic Pi source. puts and warn are diagnostics, not generated code.

bpm = 120
notes = [60, 64, 67, 72]
steps = notes.map { |n| "  play #{n}, amp: 0.4\n  sleep 0.25" }
"use_bpm #{bpm}\n\nlive_loop :generated do\n#{steps.join("\n")}\nend\n"
  1. Choose Script, edit or open a trusted generator, then choose Gen/Cancel.
  2. Review and approve the trust warning. Ruby has normal file, command and network access. This is not a sandbox.
  3. Read the result in Preview. Errors also appear there; Code is unchanged.
  4. Use Append, or confirm Replace, to change Code.
  5. Press Run separately for sound. Undo gen restores the prior Code until you make later manual edits; pressing it again redoes the change.

Gen/Cancel cancels an active worker. Stop stops audio, not generation. Limits: one worker per instance, 5 seconds, 64 KiB script, 32,000 UTF-8 output bytes, and 16 KiB diagnostics. Empty output, failures, stale results and oversized additions cannot erase Code. Editing the script or restoring a project invalidates a running result.

Generators run in a temporary working directory, separate from the audio runtime. Do not depend on the host’s working directory. Use explicit paths for any data you read. Double-quoted Ruby strings interpret \n as a newline; single-quoted strings preserve it literally.

Syntax colours help distinguish Ruby keywords, comments, strings, symbols, numbers and Sonic Pi names. The lower output area shows runtime or generator messages. Switching Code/Script/Preview reloads the text editor and resets its local typing undo history. Generator undo and Snips undo are separate protected actions.

7. Troubleshooting

No sound

Check the host audio engine and stereo output routing, wait for runtime readiness, use Code view and press Run. Confirm the program ends with end, not en. Look at the runtime messages and RuntimeData/spider-runtime.log. The instrument does not need host tempo synchronization.

Runtime will not start or files will not save

Keep the complete self-contained bundle and move it to a writable directory. RuntimeData, Snips and Files live inside that folder. There is no hidden AppData fallback. A DAW may require a rescan after you move the plug-in. Missing bundled runtime files require reinstalling the complete package, not just its binary.

A snippet is not listed

Put a regular UTF-8 .rb or .txt file directly in Snips, not a nested folder or symlink. Reopen the Snippets menu. More than 128 files produces an explicit limit error rather than hiding files.

A snippet no longer plays

Check the exact tested source in the bundled report. A changed or newly added file is unverified. Look for runtime errors, duplicate loop names or unavailable external files. A snippet can be valid on its own but conflict with the program it is appended to. Stop and test unfamiliar code separately after saving your current work.

A generator fails or returns nothing

Its final expression must be a String. Put Sonic Pi commands inside that String rather than calling them as generator Ruby. Review Preview for syntax errors, exceptions, timeouts and size limits. Empty output is deliberately prevented from replacing Code.
